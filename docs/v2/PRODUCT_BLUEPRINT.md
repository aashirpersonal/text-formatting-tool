# Product blueprint — text transformation tool (v2)

**Status:** Approved product direction. A mobile-first simple transform flow exists at `/app`, with the manual recipe editor at `/app/advanced`. Secure schema-constrained AI recipe generation exists behind `RECIPE_GENERATOR_MODE` (default prototype). See `docs/v2/AI_RECIPE_GENERATION_V1.md`.
**Date:** 2026-07-28
**Related:** `docs/v2/ARCHITECTURE_DECISIONS.md`, `docs/v2/UX_RESET_V1.md`, `docs/audits/2026-07-28-legacy-v1-baseline.md`, `docs/evidence/EVIDENCE_REGISTER.md`

---

## A. Product statement

v2 is an **AI-guided, deterministic, and privacy-conscious large-text transformation tool**.

In the intended product:

1. The user provides text or a supported text file.
2. The user describes a **deterministic** transformation in plain language.
3. The user reviews **representative samples** (and may redact them).
4. **Only** the approved samples and the instruction may leave the browser (to a secure server-side model API).
5. The model returns a **structured transformation recipe** (versioned JSON), not executable code.
6. The recipe is **explained and validated** against an allowlisted schema.
7. The user **previews** the transformation on samples (and optionally a bounded excerpt).
8. A **trusted browser-local engine** applies the approved recipe to the **complete** document.
9. Results are **deterministic and repeatable** for the same input, recipe, and engine version.

**Hard rule:** The model must **never** generate JavaScript (or any other code) that the application executes—including via `eval`, `Function`, `new Function`, injected scripts, generated workers, or dynamic imports of model output.

## B. Target users

Practical audiences include:

| Audience               | Example needs                                                                                 |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| Developers             | Cleaning logs, normalizing generated output, reshaping fixture dumps                          |
| Analysts               | Cleaning exported CSVs/pasted tables before spreadsheet or BI import                          |
| Researchers            | Standardising text collections, reference lists, repeated field formats                       |
| Ecommerce / operations | Cleaning product titles, SKUs, order notes, inventory lists                                   |
| Administrators         | Processing repetitive line lists, access logs excerpts, directory exports                     |
| Students / educators   | Transforming structured notes, bibliographies, assignment corpora                             |
| Content teams          | Predictable format conversions (delimiters, headings, repeated labels)—not creative rewriting |

The product optimises for **rule-like, inspectable transforms** on **large** text, not open-ended generative editing.

---

## C. Jobs to be done

Representative deterministic jobs:

- Normalise dates into a single format
- Clean copied spreadsheet / TSV / CSV-like text
- Convert delimiters (comma ↔ tab ↔ pipe, etc.)
- Extract repeated patterns into a cleaner list
- Remove duplicate lines (exact or normalised)
- Rename repeated labels or prefixes/suffixes
- Convert predictable logs into tabular text
- Standardise reference lists
- Filter or reorder structured lines
- Apply a saved recipe repeatedly to very large documents

---

## D. Explicit non-goals

v2 will **not** position itself as, or silently attempt:

- Unrestricted arbitrary code execution (legacy v1 failure mode)
- General-purpose semantic rewriting (“make this sound better”)
- Factual correction or knowledge updates
- Creative rewriting or stylistic paraphrase as a core promise
- Open-ended summarisation as a deterministic engine feature
- Translation where meaning must be generated by a model over the full document
- Pretending that every natural-language request can be expressed as a safe deterministic recipe

When a request cannot be mapped to allowlisted operations with clear semantics, the product should **refuse or ask for refinement**, not fall back to executing model-written code.

---

## E. Primary user journey

1. **Add input** — paste text or open a supported text file; preserve the original.
2. **Describe the transformation** — plain-language instruction aimed at deterministic behaviour.
3. **Review and redact samples** — system proposes representative samples; user approves, edits, or redacts before any network call.
4. **Generate a recipe** — server calls the model with instruction + approved samples only; returns a versioned `TransformationPlan`.
5. **Review the explanation** — human-readable summary of each allowlisted step and risk notes (e.g. regex).
6. **Preview changes** — apply the plan to samples / a bounded excerpt; show a visual diff.
7. **Approve** — explicit user confirmation before full-document run.
8. **Run locally** — trusted engine executes in a Web Worker over the full document.
9. **Monitor or cancel** — progress reporting and cancellation.
10. **Inspect results** — counts, warnings, structured failures; optional full diff for manageable sizes.
11. **Export, undo, or save the recipe** — download result; restore original / bounded history; export a **data-free** shareable recipe.

## G. Later features

After the core engine and trust model are proven:

- Batch processing of multiple documents
- CSV-aware operations
- Folder processing where the platform supports it
- Offline PWA behaviour for local-only runs of saved recipes
- CLI and npm package for the transformation engine
- Public recipe gallery (data-free plans only)
- Developer API for plan validation / execution
- Community-contributed allowlisted operations (reviewed)
- Opt-in anonymised product analytics (never logging document/sample contents by default)

## H. Product differentiation

| Not this                                 | Why v2 differs                                                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| A regex generator                        | Regex is one high-risk allowlisted op inside a broader validated plan, with preview and limits—not the product identity |
| A normal AI text editor                  | Full document stays local; model sees samples only; output is a recipe, not rewritten prose                             |
| An LLM chunking wrapper                  | We do not stream the whole corpus through a model to “transform” it                                                     |
| A local LLM application                  | Cloud model may assist recipe authoring; execution is a trusted deterministic engine                                    |
| A collection of basic formatting buttons | Buttons may remain as shortcuts that emit plans; the core asset is the recipe + engine + privacy boundary               |

**One-line positioning:** AI helps author an inspectable transformation plan; a trusted local engine applies it at scale.

---

## I. Relationship to legacy v1

Legacy Create React App v1 demonstrated demand for AI-assisted text transforms but used an unsafe execution model and browser-held API keys. v2 **rebuilds** the product on a new architecture rather than visually refreshing v1. Git history on `master` is preserved as evidence; active development proceeds on `v2-rebuild`.
